## D-003 — Tooling without Docker · 2026-11-14 · ACCEPTED
Dev machine has no Docker/PostgreSQL/Redis. Tests and local dev run against a **real** PostgreSQL via `embedded-postgres` (`pnpm db:dev`, `infrastructure/scripts/with-db.mjs`); Docker Compose + CI use the official `postgres:17` image. No mocked database anywhere in tests. Redis is optional in dev with PostgreSQL/in-memory fallback.

## D-004 — Prisma 6 + hand-written SQL · ACCEPTED
Prisma 6.19 (stable) rather than the 7/8 release candidates. Advanced constraints are SQL in `0002_constraints`. Baseline `0001_init` generated by `prisma migrate diff`; later migrations are additive.

## D-005 — Turborepo + pnpm · ACCEPTED
Packages build with `tsc` to `dist`; apps depend on `workspace:*`. Turbo orders `build → test`.

## D-006 — Custom first-party auth · ACCEPTED
HS256 access JWT (15 min) containing only `sub`, `sid`; **permissions are re-read from the DB every request** so suspension/role change/logout is immediate. Refresh tokens: opaque 48-byte, SHA-256 at rest, rotation with family revocation on reuse. Browser: HttpOnly cookies + double-submit CSRF; non-browser: `X-Token-Delivery: body`. Tokens are body-delivered on refresh only when the client supplied the token in the body (so a script cannot extract cookie-held tokens).
*Trade-off:* one DB read per authenticated request; acceptable for the prototype, cacheable later with Redis + explicit invalidation.

## D-007 — `access_logs` partitioning deferred · OPEN
Prisma can't model partitioned tables with composite PKs cleanly. Plan: raw-SQL migration in Phase 9 (monthly range partitions on `occurred_at`) with the retention job. Present indexes meet current volumes.

## D-008 — MFA policy · ACCEPTED (configurable list)
Required for `SUPER_ADMIN`, `ICT_ADMIN` (`MFA_REQUIRED_ROLES`). Un-enrolled privileged users get a session limited to MFA-setup routes. Available to all users. TOTP (RFC 6238) + 8 single-use recovery codes. KIU may extend the list.

## D-009 — Privilege-escalation controls · ACCEPTED
Only `SUPER_ADMIN` may grant `SUPER_ADMIN` or modify a Super Admin; nobody may change their own roles/status; role/status changes need a reason and revoke target sessions; `STUDENT` role is not assignable to staff.

## D-010 — Deny-by-default routes · ACCEPTED
`PermissionsGuard` rejects any route lacking an explicit policy decorator, so a forgotten decorator can never open an endpoint.

## D-011 — Facts default fail-closed · ACCEPTED
New students start with no registration, 0 % fees, nothing cleared. Unknown facts at decision time ⇒ DENY (`FACT_UNKNOWN`).

## D-012 — Seed conventions · ACCEPTED
`exam_cleared = fees ≥ 100 %` in demo seed **only** as a convention; real clearance is a Finance-set fact and the threshold is a configurable rule value (PDF's 100 % is an example, not KIU policy). All demo records carry `is_fictional = true`. Demo seeding refuses to run in production.

## D-013 — Biometrics · ACCEPTED (defaults)
Face is an alternative *credential*, never an eligibility bypass; online-only; 1:1 default, 1:N behind a default-off flag; mock adapter must be labelled “prototype-only”; no templates in browser caches. Card LOST ≠ account suspended: a lost card does not by itself disable a separately authorised face credential (policy in `biometric_policies`, tested as FACE-06).

## D-014 — Offline policy defaults · ACCEPTED
`GATE: CACHED_ALLOW`; every other service `DENY_ALL` offline (exam/meal double-spend & freshness). Cache validity short; revocation version in manifest.

## D-015 — Audit design · ACCEPTED
Hash-chained (`SHA-256(prev|canonicalJSON)`), appended under `pg_advisory_xact_lock`, UPDATE/DELETE/TRUNCATE blocked by trigger; `GET /audit/verify` recomputes. The trigger does **not** stop a superuser disabling it — detection (chain verification) plus external anchoring (periodic export of the head hash) is the control; anchoring is Phase 10.

## D-016 — AES-CMAC implementation · 2026-11-14 · ACCEPTED (revisit before real use)
Node's `crypto` has no AES-CMAC, so `packages/vcard/src/cmac.ts` implements RFC 4493 on the platform's AES block primitive. It is checked against all four RFC 4493 vectors and used only for diversification, proofs and MACs. *Why not a library:* none was vetted in this environment; *risk:* home-grown composition. Replace with a reviewed library or an HSM/SAM before any production use.

## D-017 — The server is the SAM · ACCEPTED
Readers never hold the card master key. They relay challenge/response frames to `/access/tap/begin|auth` over their HMAC channel and the API derives `Kc = CMAC(master, UID‖AID)`. This keeps the master key off every reader and lets revocation/status be evaluated in the same call. *Trade-off:* a tap needs three round trips (≈ 25 ms locally); a physical-reader/DESFire deployment would put a SAM at the reader or in an HSM.

## D-018 — Wallet activation and key custody · ACCEPTED
Issuance creates a PENDING card + one-time activation code (hash stored). The student's device generates its **own** Ed25519 key, proves possession by signing `KIU-ACTIVATE:<cardNumber>`, and only the public key is stored: the server never holds a QR signing key. The AES card key (derived) is returned to the wallet at activation because a virtual card has to carry it; this is a documented limitation (browser ≠ secure element). A new phone = new activation code; the previous device key is revoked. There is deliberately no `GET /me/card/qr`.

## D-019 — One monotonic counter per card · ACCEPTED
QR tokens and AES reads draw from the same counter (`VirtualCard.nextCounter`), checked atomically (`txCounter < n`). Two counters would make normal alternation between QR and tap look like cloning. The simulator and tests enforce this.

## D-020 — Reader traffic is throttled per reader, not per person-IP · ACCEPTED
Found during live measurement: a per-IP 120/min limit would throttle many gates behind one campus NAT (spec: ≥ 20 students/min/reader, 3 calls per tap). Readers get 600/min per key plus a 6 000/min/IP ceiling so spoofed key ids cannot bypass limiting; people and credential routes keep their per-IP limits. All values are env-configurable and tested (`throttle.e2e.ts`).

## D-021 — Simulator is an HTTP-only CLI first · ACCEPTED
`@kiu/simulator` talks only to the public API (fetch for the CLI, supertest in tests), so it cannot fake a decision. The web simulator UI (drag-to-tap, protocol timeline, reader lab) is Phase 5/6 and will reuse the same `SimWallet`/`ReaderClient`.

## D-022 — LOST is final; unblock never resurrects a credential · ACCEPTED
`unblock` works only for BLOCKED cards; LOST returns 409 `LOST_CARD_FINAL`. A replacement always gets a fresh UID, card number, activation code and device key. Entitlements stay on the student record, so nothing is migrated.

## D-023 — `incremental` TypeScript builds disabled in the API · ACCEPTED
Combined with Nest's `deleteOutDir`, stale `.tsbuildinfo` made `tsc` skip emitting files into the freshly emptied `dist/`, producing a partial build (seed scripts missing). Correctness over build speed.

## D-024 — Phase 5 apps are Vite + React SPAs/PWAs, not Next.js · 2026-11-14 · ACCEPTED
The wallet and reader are client-side programs: device keys, WebCrypto signing, IndexedDB, camera and offline operation are the point, and SSR adds nothing. Both are Vite + React 18 + TypeScript, installable as PWAs with a small service worker. **Next.js stays the choice for the admin console (Phase 6)**, where server rendering and role-based routing help. This deviates from the prompt's "student-portal (Next.js PWA)"; the API contract is identical and the portal can be moved later without touching the API.

## D-025 — Plain CSS driven by design tokens instead of Tailwind/shadcn (for now) · ACCEPTED
`packages/ui` ships `tokens.css` + small React components (consumed as TypeScript source). This gets the neo-brutalist system, 44 px targets, focus states, reduced-motion and responsive tables in place with no build-tool coupling. Tailwind/shadcn can be layered on in Phase 6 if the admin console needs the component breadth.

## D-026 — Offline model: signed list, pinned signer, local decision, idempotent reconciliation · ACCEPTED
`GET /readers/:id/allowlist` returns a manifest signed with an Ed25519 key (`CACHE_SIGNING_KEY`); the reader pins the signer on first contact (trust-on-first-use over its HMAC channel) and rejects any other signer, wrong reader/service, expired manifests and **version rollbacks** (which could hide newer revocations). Only services with `offlinePolicy = CACHED_ALLOW` receive any cards (GATE); everything else gets an explicit `DENY_ALL` manifest, so exam and cafeteria readers fail closed. Only QR public keys are shipped: AES card keys never leave the server, so **tap is online-only**. The manifest carries the minimum per card (card number, public key(s), display name, expiry). Offline decisions use WebCrypto Ed25519 and are queued with idempotency keys; the server de-duplicates by batch key and by entry key, raises the card counter to the offline value (so the same QR cannot be replayed online later), and flags grants made after a revocation (`OFFLINE_STALE_GRANT`, HIGH alert). **Unavoidable:** an isolated reader cannot know about revocations after its last sync; the list lifetime (30 min default) bounds the exposure.

## D-027 — Wallet key custody · ACCEPTED
The wallet generates its Ed25519 key with WebCrypto as **non-extractable** and keeps the CryptoKey in IndexedDB; the page can sign but cannot read the key. Only the public key and a proof-of-possession reach the server. The wallet deliberately discards the AES card key returned at activation (a browser cannot tap), so it never holds the tap secret. The QR counter is time-seeded (`max(last+1, unix seconds)`) and persisted before a token is shown, so it can neither repeat nor fall behind the server after a storage reset. *Consequence:* a card is used either through this wallet (QR) or through the simulator's AES key, not interchangeably, because the QR counter runs ahead of small tap counters.

## D-028 — Reader secret handling · ACCEPTED
The reader imports its HMAC secret as a non-extractable `CryptoKey` and stores that in IndexedDB; the plaintext is never persisted (tested). A page-level compromise can still *use* the key to sign, which is why readers are individually revocable and rate-limited.

## D-029 — Browser virtual tap deferred · OPEN
The simulator CLI does the AES-CMAC tap. A browser version needs AES-ECB single-block (not offered by WebCrypto) for CMAC, so it needs a vetted pure-JS AES/CMAC library, not hand-written crypto. The reader's `VIRTUAL TAP` option is shown **disabled with an explanation** until then; `SCAN FACE` likewise until Phase 6.

## D-030 — Verification of colour contrast · ACCEPTED
axe-core cannot evaluate text over gradients, and the first ID-card gradient (white on `#8964F8`, 4.01:1) passed axe but failed WCAG AA. A token-level contrast test (`contrast.spec.ts`) now computes ratios from `tokens.css`, including every stop of the card gradient. The card gradient was darkened (`#5B3FD0 → #3F2A9E`, ≥ 6.8:1).

## D-031 — The admin console is also a Vite SPA (reverses part of D-024) · 2026-11-14 · ACCEPTED
D-024 kept Next.js for the admin. With a separate API and HttpOnly-cookie sessions, server rendering buys nothing (the API cannot be called from a Next server with the browser's cookie without a proxy) and would complicate auth and testing. The console is a Vite + React SPA like the other two apps and shares `packages/ui`. Revisit only if SEO/SSR or a BFF becomes a requirement.

## D-032 — Hand-written accessible SVG chart instead of Recharts · ACCEPTED
The only chart so far is hourly traffic. `BarChart` (SVG with an `aria-label` summarising every bar, a colour-independent legend, and the same numbers in the tables beside it) avoids a ~100 kB dependency. Recharts can be adopted if richer analytics (Phase 8 reports) need it.

## D-033 — Dashboard and overview are sectioned by permission, not by role name · ACCEPTED
`/dashboard/summary` and `/students/:id/overview` decide what to include from the caller's permissions, so a new custom role gets the correct view without code changes, and no role sees more than its permissions allow.

## D-034 — UI measurements wait for settled animations · ACCEPTED
Layout and axe checks in the browser suite first await finite CSS animations (`settle()`), because sampling during a 200 ms fade or slide produced false failures (43 px "targets", mid-fade contrast). Infinite animations (loading shimmer) are excluded so they cannot hang the check.

## D-035 — Gate direction: an unspecified direction is not tracked unless policy says so · 2026-11-14 · ACCEPTED (placeholder policy)
Anti-passback needs ENTRY or EXIT on every gate scan. Existing readers, the simulator and several tests scan the gate without one, so refusing those scans would break working flows before KIU has said what it wants. The policy value `gate_direction_required` (default **false**, a placeholder awaiting KIU) decides: when false, a gate scan with no direction is judged by the rules only and leaves presence untouched; when true it is refused with `DIRECTION_REQUIRED`. **Risk:** with the default, a reader that never sends a direction gets no anti-passback protection at all. Operators should set the policy to true once every gate reader sends a direction. The protection itself (ENTRY after ENTRY → `ANTI_PASSBACK`, EXIT always recorded) is done by one atomic `INSERT … ON CONFLICT DO NOTHING` plus a conditional `UPDATE` on `presence_state`.

## D-036 — Timetable and meal windows use the server's local clock · 2026-11-14 · ACCEPTED (placeholder)
Lecture times (`HH:MM` + weekday) and meal sittings are compared with the API server's local time. No campus timezone setting exists yet, and none was specified. A deployment in another timezone would shift every window. A `campus_timezone` system setting is the intended fix. Lecture entry opens 15 minutes before the start (a constant, to become a setting).

## D-037 — One meal per sitting and one lecture mark per day are database constraints · 2026-11-14 · ACCEPTED
`meal_usage` is unique on (student, sitting, day) and `lecture_attendance` on (schedule, student, day). The rules decide *whether* a student may eat or attend; the unique key decides *whether it already happened*, so two simultaneous scans cannot both succeed whatever the credential type. The meal is claimed only after the rules allow it, so a denied scan never consumes a sitting. Known edge: the claim happens just before the access log is written; if that write then fails, the meal stays claimed and the student sees an error. This fails safe (no double meal) but needs a staff correction.

## D-038 — Face is built with a labelled prototype adapter, in-process, 1:1 only · 2026-11-15 · ACCEPTED (user directed the build)
The user chose to build the face route now. Because no approved SDK, evaluation evidence or privacy review exists, the engine is `MockFaceAdapter` (cosine similarity of 24×24 luminance thumbnails, mock motion "liveness"). It exists to prove the whole pipeline, **not** to recognise faces reliably, and every surface says so (`is_mock` on the model version, PROTOTYPE badge on capture, console and reader banners, student portal note). The adapter sits behind the `FaceAdapter` interface so a vetted SDK can replace it. Consequences: (1) matching runs in-process in the API rather than in a separate biometric service, so there is no signed assertion between them yet (BIO-08 ⬜); (2) the browser sends only five 24×24 luminance frames, never an image; (3) 1:1 only (the reader sends the claimed registration number), 1:N is not implemented; (4) a printed photo that is moved by hand can pass the mock liveness check, so no spoof-resistance may be claimed; (5) there is no per-student failed-attempt lockout yet.

## D-039 — Face enrolment is compulsory for every student (supersedes the "optional" part of D-013) · 2026-11-16 · ACCEPTED (user directive)
The user directed that face enrolment be compulsory ("THIS SHOULD BE COMPULSORY", then chose "Face enrolment for every student"). This reverses the earlier design rule that face is optional. What was built, and what it does not settle:
* **Policy** (\`biometric_policies\`): \`ENROLMENT_REQUIRED\` (default **true**; the institution can switch it off) and \`ENFORCE_FROM\` (a date, default **none**). Until a date is set, students are told and tracked but nothing is refused; from that date every credential (card, QR, face) is refused with \`FACE_ENROLMENT_REQUIRED\` unless the student is enrolled or exempt. Offline readers use their cached list and do **not** enforce this. A manual override cannot bypass it (the remedy is to enrol or be exempted).
* **Exemptions** (new table \`biometric_exemptions\`, migration 0005): staff with \`biometrics.policy.manage\` can excuse a student (reason of 10+ characters, audited, student notified). An exempt student keeps using card and QR. This exists because a compulsory biometric needs a route for disability, safety or conscientious objection; without it the scheme would exclude people.
* **Notice** changed accordingly (\`KIU-FACE-NOTICE-2026-02-prototype-compulsory\`): it no longer says "optional" or "withdraw" and it tells students about exemptions. Enrolment records the lawful basis as \`INSTITUTIONAL_REQUIREMENT\`, not \`CONSENT\`. If the requirement is switched off the old voluntary notice and \`CONSENT\` basis return.
* **Deletion:** students can still delete their template; while enrolment is compulsory that puts them back in the "must enrol" state (and, after the enforcement date, locks them out until they re-enrol or are exempted).
* **Not settled, and not claimed:** this repository does **not** show that a compulsory face programme is lawful at KIU. Consent can no longer be the legal basis; the Uganda Data Protection and Privacy Act, 2019 needs a lawful basis, a data-protection impact assessment, a retention schedule and probably the regulator's involvement before real use. The engine is still the prototype mock (no accuracy or anti-spoofing evidence). A compulsory scheme built on an unvalidated engine would lock out genuine students on false rejections and admit impostors on false accepts; the card/QR fallback only helps if enforcement is not tied to successful face verification (here it is tied to enrolment only).
